# Live verification (Ubuntu 22.04 reference VPS)

These checks were run read-only against a working server. No live HAProxy or
OpenVPN configuration was modified.

## Observed baseline

| Item | Value |
|---|---|
| OS | Ubuntu 22.04.5 LTS |
| OpenVPN | 2.5.11 |
| HAProxy | 2.4.30 |
| Public listener | HAProxy `*:443` |
| Existing frontend | `unified_443` |
| Existing VPN backend | `bk_ovpn` → `127.0.0.1:11944` |
| Existing profiles | `remote … 443`, TCP, TLS 1.3, `tls-crypt` |
| Server certificate CN | `ChangeMe` (RSA 2048, CA-signed) |
| Existing PKI | `/root/easy-rsa/pki` |
| Certificate verification | `verify-client-cert none` + PAM |
| MTU / MSS / buffers | 1400 / 1360 / 524288 / 524288 |

## Detection result

`vpn-installer plan` on that server reports:

```
action: reuse
reason: existing route already points to OpenVPN
frontend: unified_443
backend_port: 11944
```

The generated server config keeps the live port (`11944`), SHA384, TLS 1.3,
MTU 1400, MSS 1360, buffers 524288, `verify-client-cert none` and
`duplicate-cn`.

## HAProxy safety proof

`HAProxyManager.apply()` was run against a **copy** of the live config. It
returned:

```
changed=False, reused_existing=True, backup=None
```

The SHA-256 of the config was identical before and after. No frontend,
backend, route or certificate was changed.

## Profile handshake proof

A profile generated by this project from the existing PKI was used with a
deliberately wrong password. The client log showed:

```
TCP connection established with 168.222.43.203:443
TLS: Initial packet …
VERIFY OK: depth=1, CN=ChangeMe
VERIFY OK: depth=0, CN=ChangeMe
Control Channel: TLSv1.3, cipher TLSv1.3 TLS_AES_256_GCM_SHA384,
                 peer certificate: 2048 bit RSA
AUTH: Received control message: AUTH_FAILED
```

That proves the TLS/crypto/port path and certificate pinning work end-to-end.
`AUTH_FAILED` is the expected result for the intentionally wrong password.

## PKI proof

A temporary copy of `/root/easy-rsa/pki` was used. The PKI step:

- reused the existing RSA CA and server certificate,
- adopted the existing `ta.key`,
- issued a new, unique client certificate (`CN=keytest`),
- generated a valid CRL (642 bytes, not an empty placeholder),
- verified the chain with `openssl verify`.

No live certificate or key was modified.
